1. Opening 2 min

Thank you for your time. In the next forty minutes I want to show you one thing: when a developer changes code, TIA tells your testers exactly what that change affects and which of their test cases to run again, in their language, before the change is merged.

I will use a small, made-up bank called Northwind Pay, so we can see every result without touching your code. Everything you will see today is computed live from the code on this laptop.

2. The problem 2 min

Here is the situation most teams are in. A developer changes one service. The tester gets a ticket that says "updated payments API". Now the tester has to guess: which other systems use this API? Which screens? Which of my test cases are affected?

Usually there are two answers. Either we retest everything, which is slow and expensive, or we guess, and the defect we missed shows up in production, often in a different team's system.

TIA replaces the guess with evidence. It reads the code of all your services, builds a map of who depends on whom, and for each change follows that map to everything affected. And for every claim it makes, it shows you the file and line that prove it.

4. The map of the code 4 min

Section 2. Code graph: choose level service and load the graph.
payments-api in the middle, with statement-service, mobile-bff and web-portal calling it, and the topic payments.created consumed by statement-service.

This is the map TIA built by reading the code. Nobody drew it and nobody declared it. TIA found the calls in each service's code and matched them to the API that answers them.

Each line is a dependency, and its colour says how sure TIA is. A solid line means TIA found the actual call in the code. If TIA can only guess, for example because two APIs look alike, it draws the line differently and labels it as a guess. It never presents a guess as a fact.

5. Change 1: a breaking API change 9 min

Now a developer makes a change. They remove a field called disputed from the payment-history API, because payments-api itself no longer needs it. Their own tests pass. Let us see what TIA says.

Section 1. Repositories → Upload zip: upload zips/scenarios/04-feature-remove-disputed/payments-api.zip with the name payments-api. Then press Analyse vs previous upload, then Run analysis.

I upload the changed version of payments-api and ask TIA to compare it with the previous one. That is all the input it needs.

The tester's answer first

Section 4. Report: stay at the top, the What to test block.
Regression-test 4 of your 14 test case(s): NW-06 Payment history, NW-08 Accounts screen shows the balance, NW-11 Statement leaves out disputed payments, NW-12 Mobile activity shows every payment. NW-14 is listed under review by hand.

This is the first thing your tester sees: four of your fourteen test cases need to run again, and here they are by name. Each one has a reason: which screen or API it tests, and how the change reaches it.

Notice what is not on the list. Ten cases are not affected, so your team does not spend time on them.

And notice NW-14, "Archive export reaches the archive". TIA cannot connect that test case to anything in the code, so it does not pretend. It puts it under "review by hand". It never silently drops a test case.

The engineer's answer

Scroll to the Findings table.
A critical finding on statement-service and a high finding on mobile-bff, marked breaking.

For engineers, the same result as findings. statement-service is critical: the change breaks it, and statement-service is marked as a critical service. mobile-bff is high: also broken, but less critical.

The severity is not an opinion. It comes from a fixed rule table: was the change breaking, is the link proven, how critical is the affected service. Each finding names the rule that produced it. Your organisation can tune those rules, and every change to them is recorded.

Press Show in the Graph column of the statement-service row, then read the Why column aloud.

And here is the proof. The changed response, the API that returns it, and the exact line in statement-service that calls it. File and line. An engineer can open that file and check it in ten seconds.

The defect nobody asked about

Back in What to test: point at Possible rule gaps and Consistency checks.
One rule gap: statement-service leaves out disputed payments; mobile-bff does not. One consistency check on the shared API.

This is my favourite part. TIA noticed something nobody asked it about. The statement leaves disputed payments out. The mobile app shows all of them. Same data, two different business rules.

Maybe that is intended, maybe it is a defect. Either way, a customer could see one total in the app and a different total on their statement. TIA found that by reading the code, and it tells you exactly where the rule is applied and where it is missing. Now your tester knows to compare those two screens for the same account.

The tester pack

Press Tester pack. Open its three tabs one by one.
The coverage gate per affected entry point; the API test matrix; the UI locator pack.

Finally, everything a tester needs for this one change, in one place. First, for each affected API: are your existing tests enough, and if not, which aspects are not covered. Second, the test matrix for the affected APIs: valid values, invalid values, boundaries. Third, for the affected screens: every field and button, and how an automation script can find it reliably.

6. Change 2: a new setting 4 min

Second change, a quieter one. The developer adds a feature behind a switch: the balance now subtracts money that is on hold, but only when a new setting, HOLDS_ENABLED, is turned on. This is exactly the kind of change that passes code review and then behaves differently in the test environment.

Upload zips/scenarios/01-feature-holds/payments-api.zip as payments-api → Analyse vs previous upload → Run analysis.
Regression-test 5 of your 14: NW-01, NW-02, NW-03, NW-07, NW-08. Under Configuration: balance_of now reads HOLDS_ENABLED; no file sets it; held_amount already reads the same key.

Five test cases this time: creating a payment, the minimum-balance refusal, the amount limit, the balance itself, and the accounts screen.

And look at the configuration check. TIA says: the code now reads HOLDS_ENABLED, and no configuration file in the repository sets it. So before your tester starts, someone has to set it in the test environment. Otherwise the tester is testing the old behaviour and reports "all passed". That is a lost day, and TIA prevents it with one line.

It also says another function already reads the same setting. Change it, and that function's behaviour changes too.

The related scenario 02 (MIN_BALANCE raised from 80 to 100 in a config file) gives "Regression-test 3 of your 14". If asked whether TIA shows secret values: it reports only that a value changed, never the value.
Upload zips/base/payments-api.zip again.

9. Why you can trust it 4 min

A tool like this is only useful if you can trust it. Four things.

One: there is no AI guessing in the analysis. TIA reads the code with parsers and applies a fixed rule table. Same code, same settings, same answer, every time. You can ask it to re-run an old analysis and it confirms the result is identical.

Two: it shows its evidence. Every finding ends in a file and a line.

Three: it tells you what it does not know.

Scroll to Unknowns in the current report.

Every report has this section. Calls it could not resolve, systems outside the code it was given, files it could not read. A clean report with unknowns is not a clean bill of health, and TIA says so instead of hiding it.

Four: it never runs your code and never blocks your developers. It reads code as text. Its pull-request comment is advice; your process decides.

10. How it fits your process 2 min

Today I clicked buttons, but in daily use nobody has to. When a developer opens a pull request, TIA runs automatically and posts one comment on it: what is affected, what to retest, and a picture of the services involved. Each new push updates the same comment.

Your test management tool, your pipelines and your AI assistants can ask the same questions through an API. And it runs inside your own network if you need it to, with no connection to the outside.

11. Close and next step 1 min

To sum up: for every change, TIA tells your testers which test cases to run again and why, finds the rule differences between your systems, tells you about settings that must be in place, and says plainly when a change needs no testing at all.

12. Questions and honest answers

Answer exactly this much. Do not round up "tested against a stand-in" to "works with".

They askYou answer
Is this AI?No. The analysis uses parsers and a fixed rule table, which is why it is repeatable and every claim cites a file and line. AI assistants can consume its results.
Which languages and frameworks?In depth, including HTTP links between services: Python, Java, Kotlin, C#, Go, TypeScript and JavaScript; front end Angular, React, Vue, HTML; data JPA, SQLAlchemy, Django, Entity Framework, SQL and stored procedures, Kafka. For 39 more languages, among them Rust, Ruby, PHP, C and C++, Scala, Swift, Dart and Elixir, TIA reads the structure: functions, classes, calls and tests. A change there reaches its callers and tests, and the report says that HTTP links in those languages are not read.
How accurate is it on our code?Not measured yet. It met its accuracy targets on real Java code bases and test landscapes. That is exactly why the next step is a pilot on your code.
What can it miss?Anything not visible in the code: addresses built at run time, systems outside the repositories it is given. It lists these under Unknowns rather than hiding them.
Does it run or copy our code anywhere?It never runs it; it reads files as text. Secrets found in code are kept out of its records and reports. People only see results for repositories they are allowed to read.
Can it block a release?Not by default. It is advisory. An organisation can configure release rules, and an enforcing mode reports a failed mandatory rule to the pull-request check.
GitHub, GitLab, Azure DevOps, ServiceNow?The GitHub pull-request comment is verified on github.com. GitLab, Bitbucket, Azure DevOps and ServiceNow are built and tested against simulated services, not yet against the real ones.
Is it secure for several customers on one system?Each customer's data is isolated inside the database itself, and that is tested. An independent penetration test has not been done yet.
How big a code base?Measured on 500 generated repositories (0.6 million lines): a pull-request analysis in under 9 seconds at the 95th percentile. Larger sizes are not measured yet.
Can we put our own brand on it?Not as a setting today; the name is fixed in code. It is a small, scoped piece of work.
What do we need to run it?A PostgreSQL database and one container image (an API process and one or more workers). No GPU and no external service.
