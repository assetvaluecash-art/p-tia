Twelve steps, left to right, from bringing the code in to publishing the result. Step 1. Bring the code in

Copy each repository into TIA and keep it up to date

Goes inA repository address (or a zip / folder)
→
Comes outA local copy of the repository with all its branches, and a record of when it was last synced

TIA can only analyse code it has. So the first step is to give it every repository that matters: the service being changed and the services that use it. In our example that is three repositories: payments, statement and portal.

A repository can come from GitHub, GitLab, Bitbucket, Azure DevOps or any git address, or be uploaded as a zip or folder. TIA keeps its own copy and fetches new versions when asked (a sync), or automatically when a pull request arrives.

Why it matters: if a service that uses payments is not in TIA, TIA cannot see that it breaks. The report says so (step 10, unknowns), but it cannot invent what it was never given.

How it works inside, in order

Registering a repository (RepoService.register):

  1. Check the address: only https, http, ssh, file or a local path. A password inside the URL is refused (tokens go in a separate field, and only over https). If the server has an allow-list of hosts, the host must be on it; an address that points at the server's own network is refused.
  2. Run git clone --bare --no-tags <url> <workspace>/<name>. A bare clone is the history only, with no working files: TIA never checks files out, it reads them straight out of git.
  3. Run git fetch --prune --no-tags origin "+refs/heads/*:refs/heads/*": copy every branch.
  4. Record the default branch, its latest commit and the list of branches in the repositories table, and write repository_registered to the audit log.

Syncing (RepoService.sync), later and before every pull-request analysis:

  1. The same fetch of every branch; branches deleted on the remote are removed (--prune).
  2. git ls-remote --symref origin HEAD: find the remote's current default branch (it may have been renamed) and point TIA's copy at it.
  3. Record the new latest commit. If the fetch fails, the repository is marked scan_status = failed with the reason, and its links to other services show as stale until a sync succeeds.

Then refresh_landscape reads every repository at its current commit (step 2) and rebuilds the map (step 3).

The files and functions

Clones a remote repository as a bare copy into the workspace folder, or registers a local path. Refuses hosts outside the allow-list and sends tokens only over https.

tia/repos.py · RepoService.sync

Fetches every branch from the remote, follows the remote's default branch, records the latest commit. A failed fetch is recorded as a failed scan with its reason.

tia/analysis_service.py · refresh_landscape

Step 2. Read every file

Turn code into facts: addresses, calls, data shapes, tests

Goes inThe files of one repository at one exact version
→
Comes outA list of facts per repository: addresses, calls, data shapes, functions, tests, pages, tables

TIA reads every file as text and writes down the facts it needs: which addresses a service offers (for example GET /accounts/{account_id}/payments), which other services it calls, the shape of the data it sends, its functions, its tests, its web pages, its database tables, and the testers' written test cases.

It never runs the code. A broken or malicious repository cannot do anything inside TIA.

Why it matters: these facts are the raw material for everything after. In our example, the fact that statement_rows reads the field disputed is what later lets TIA say the statement depends on it.

How it works inside, in order

Reading one repository at one commit (extraction.extract_commit):

  1. List every file. git ls-tree -r -z <commit> gives each file's path and its blob id, a fingerprint of the file's exact content. Only regular files are kept (no symlinks or submodules). For payments-service: app.py, tests/test_payments.py, tia-services.yaml.
  2. Read the settings files first. tia-services.yaml, catalog-info.yaml, Spring application.yml / .properties and contracts/*.json. read_service_map takes from them the service name, owner, criticality, which setting points at which service, and readable names for addresses.
  3. Choose the files to parse (is_extractable): source files (.py .java .go .cs .kt .ts .js), web templates, SQL and migrations, OpenAPI files, event schemas, written test cases. Files matching the organisation's exclude patterns are skipped and counted.
  4. Check the cache. Each file's key is: repository, service, settings, extractor version, blob id, path. Facts already stored under that key (table file_extracts) are reused. The blob id changes only when the content changes, so an unchanged file is never parsed twice; the extractor version is in the key, so upgrading TIA re-parses everything.
  5. Read only the missing files, all in one git process: git cat-file --batch. A file that is not valid UTF-8 is recorded as failed, with that reason.
  6. Parse each file with the reader for its type (extract_source): .py with Python's own parser (ast) and a visitor that walks the syntax tree; .java, .go, .cs, .kt, .ts/.js with tree-sitter parsers; OpenAPI, Avro / JSON Schema, Kafka connector files, testcases/*.csv|yaml|json and web pages with their own small readers. Nothing is imported or run.
  7. Store the new facts in the cache.
  8. Assemble (assemble): merge all files' facts into one record per repository, then resolve what spans files: ORM classes to tables, Django routes (urls in one file, views in another), Java Feign clients, and the request / response data shapes of each address.

What the Python reader takes from a file (_FileVisitor), using the example code:

  1. First pass (prepass): imports (which name is which module); module constants, e.g. PAYMENTS_BASE_URL = os.getenv("PAYMENTS_BASE_URL", ...) is remembered as config key PAYMENTS_BASE_URL (a literal "http://host/..." would be a host); APIRouter(prefix=...) prefixes; variables holding a generated API client.
  2. Each class: a BaseModel becomes a data shape with each field's type, whether it is required, and its rules (amount: float = Field(..., gt=0, le=10000) → required, greater than 0, at most 10000); an Enum gives its allowed values (EUR, USD, GBP); an ORM model becomes an entity with its table and columns; every class is recorded with its base classes.
  3. Each function becomes a function record: its id repo:file::name and lines; hash (a fingerprint of its syntax tree: any code change changes it); body_hash (the same without the docstring: if only hash changed, the change was documentation only); its signature (parameters); the names it calls; the business rules it applies to items, its filters ([p for p in payments if not p["disputed"]] → rule not p['disputed'] on field disputed); the HTTP errors it raises (404 unknown account).
  4. Addresses come from decorators: @app.get("/accounts/{account_id}/payments", response_model=List[Payment]) on list_payments → method GET, path, normalised path /accounts/{}/payments, handler, response shape Payment as a list, success status, authorisation markers, parameters with their rules.
  5. Outgoing calls: requests.get(...), httpx.post(...), session.get(...) and the like. The URL is taken apart: f"{PAYMENTS_BASE_URL}/accounts/{account_id}/payments" → GET, /accounts/{}/payments, address from config key PAYMENTS_BASE_URL. If the address cannot be worked out, the call is still recorded with the reason.
  6. Tests: test_* functions in test files, with the paths they call through a test client (client.get("/accounts/123/payments")), the statuses they assert and the bodies they send.
  7. Also: Kafka producers and consumers (producer.send("topic", ...)) and SQL written inside the code.

Step 3. Connect the services

Join the facts into one map of who calls whom

Goes inThe facts of every repository
→
Comes outOne map: points (services, addresses, functions, tests) and labelled lines between them

Facts from one repository are not enough. TIA joins them into one map: this call in the statement service reaches that address in the payments service.

Each link carries a label saying how sure TIA is: confirmed (proved from the code and the settings files), inferred (likely, but not proved) or not linked at all. Nothing is guessed silently.

Why it matters: this map is what lets a change in one service be followed into another. In our example, the link from the statement service's client.py line 9 to the payments address is the bridge the change crosses.

How it works inside, in order

Building the map (graph.build_graph), from the facts of every repository:

  1. Points. One for every service, function, class, data shape, address, outgoing call and test, each with its repository, file and line.
  2. Lines inside each repository, as in this table.
  3. Events, data and SQL: PUBLISHES / CONSUMES_EVENT through one point per Kafka topic; READS / WRITES from functions to tables; lineage through stored procedures.
  4. Lines between services (resolve.resolve_consumers): each outgoing call is matched to an address in another service by the strategies in the second table, tried in that order; a call none of them can match stays unlinked, with the reason (no endpoint found, several match, base not resolvable).
  5. Save the map as a version whose id is a fingerprint of its inputs (every repository's commit, the extractor and configuration versions): the same inputs give the same id, and the stored version is reused.

Step 4. A change arrives

From the web page, the API, or a pull request

Goes inA request: which repository, which change (branch, commit or pull request), against which base
→
Comes outAn accepted request bound to one organisation, run now or placed in the queue

A change reaches TIA through one of three doors: someone presses Run analysis on the web page, a script calls the API, or a code host (GitHub, GitLab, Bitbucket, Azure DevOps) reports a pull request.

Before any work starts, TIA checks who is asking and whether they may (sign-in and roles), which organisation it is for, and whether that organisation's plan allows another analysis. A pull-request notification is checked for its signature or password.

Pull requests are queued: TIA answers at once and a worker does the analysis. If the developer pushes again before the work starts, the older job is dropped and only the newest version is analysed.

tia/api.py · create (POST /api/v1/impact-analyses)

Checks the plan (within_plan), that the caller may read the repository (require_repo), that the server has room, then runs the analysis now or queues it (?async=true).

tia/authapi.py, tia/rbac.py

Sign-in (sessions, tokens, OpenID Connect, SAML) and the route table: every address of TIA's own API needs a listed permission, an unlisted one is refused.

tia/webhooks.py · verify_signature, parse_pull_request

Checks a GitHub notification is genuine and reads the pull request number, head commit and target branch. scmhosts.py and ado.py do the same for the other hosts.

tia/jobs.py · enqueue, claim · tia/worker.py · run_once

The queue in PostgreSQL. A job key stops duplicates; a group key lets a newer push replace an older one. Workers take jobs with FOR UPDATE SKIP LOCKED (never the same job twice), under a 5-minute lease, and retry failures with growing delays.

The request used for the example, as a script would send it:

  • Run analyses on a schedule, for example every night for the main branch against the last release. Today a person, a pipeline or a pull request starts every analysis.
  • Start an analysis from a change ticket in the ticketing system, not only from code.

Step 5. Fix the exact versions

Turn branch names into exact commits

Goes inBranch names, a pull request number or commits
→
Comes outExact commits for every repository, and the limits for this analysis

"Analyse my branch" is not precise enough: a branch moves. So TIA first turns every name into an exact commit, a fixed version of the code: the version before the change (the base), the version after (the head), and the current version of every other repository in scope.

For a pull request it also finds the point where the branch split off, so the comparison is against what the developer actually started from.

It also fixes the limits of the analysis (how far to follow, how many results, how long) from the organisation's settings. A caller can ask for less, never more.

Why it matters: with exact versions, the same analysis can be repeated later and give the same answer.

tia/analysis_service.py · resolve

Resolves head and base (RepoService.resolve), finds the merge base, resolves every other repository side by side (several at once), and caps the limits with the organisation's configuration.

tia/gitutil.py · resolve_rev

Reads a branch's commit straight from the repository's files when it can (fast), otherwise asks git. Never changes the repository.

Limits (defaults)

Follow at most 8 steps, report at most 200 results, stop after 60 seconds; the organisation's settings can lower them.

Step 6. Compare before and after

Find exactly what the change changed

Goes inThe facts before and after the change
→
Comes outThe changed items (the starting points), each with its kind of change

TIA compares the facts of the version before the change with the version after. It compares meaning, not lines of text, so it can tell kinds of change apart:

  • a change other services can notice (a field removed from data they receive, an address removed, a rule tightened),
  • a change inside a function (its logic) or to its inputs (its signature),
  • a change that only touches comments, which changes nothing,
  • a change to configuration (a setting added, removed or changed; its value is never shown, because settings hold secrets).

Why it matters: the kind of change decides everything after it. Deleting disputed is visible to other services; rewording a comment is not.

tia/impact.py · _analyze (step 2)

Reads the before and after facts of the changed repository (cached per file) and the list of changed files (gitutil.changed_files).

tia/contracts.py · diff_contracts

Compares addresses and data shapes: removed address, removed field, type change, newly required field, narrowed choices, changed authorisation. Each kind has a rule saying whether it breaks callers.

tia/data.py · diff_data

Compares database tables and columns from migrations and SQL.

tia/testscope.py · classify_function

Compares a function before and after: signature changed, logic changed, or documentation only (same code once comments are removed).

tia/configkeys.py

Finds settings that were added, removed or changed, and code that starts or stops reading a setting.

Step 7. Follow the change

Walk the map to everything the change reaches

Goes inThe changed items and the map
→
Comes outEvery reached item, with the route that led to it

From each changed item, TIA walks the map: to whatever uses it, then to whatever uses that, and so on. It follows confirmed links first, then inferred ones.

It stops at fixed limits (8 steps, 200 results, 60 seconds by default). If it stops early, the report says so: a cut-off walk is never presented as complete.

For every item it reaches, it keeps the route, step by step, with the file and line of each step. That route is the proof behind every result.

tia/impact.py · bfs (inside _analyze)

A breadth-first walk from each starting point along 'who is affected' lines. Runs twice: first over confirmed links only, then including inferred ones.

Graph.impacted_by (tia/graph.py)

For one point, the points affected when it changes, with the line that connects them. A data change follows READS or WRITES depending on what breaks.

Stopping rules

Depth limit, result limit and time budget; each sets a 'truncated' reason that appears in the report. Tests are end points: the walk does not continue past them.

Step 8. Grade each result

Fixed rules decide how serious each finding is

Goes inEvery reached item with its route
→
Comes outFindings, each with a grade, the rule that set it, and the release-rule results

Every reached item becomes a finding, graded critical, high, medium or low. The grade comes from a fixed rule table, not from opinion:

  • Does the change break the other side, or only change its behaviour?
  • Is the affected service marked critical?
  • Is the route confirmed, or only inferred? A finding reached only through inferred links is capped at medium.
  • Is it in another service, or inside the one that changed (then it is low)?

Each finding names the rule that set its grade, so anyone can check it. An organisation can adjust the rules in its settings; the change is recorded on the finding.

Then the organisation's release rules are checked, for example "no breaking change without the owner's approval". By default they only advise; they can be set to block.

tia/severity.py · compute

The rule table: breaking + affected service critical → critical (SEV-BREAKING-CRITICAL); breaking → high (SEV-BREAKING-CONFIRMED); behaviour change → medium, or high if critical; inside the changed service → low (SEV-LOCAL); inferred route → capped at medium (SEV-INFERRED-CAP).

tia/severity.py · apply_override, is_material

The organisation's own grades for a rule, and which grades count as 'material' (worth attention): critical, high, medium, or anything on a breaking route.

tia/policy.py

Release rules (no breaking change, tests passed, owner approval, analysis complete...) evaluated to pass, fail, not evaluated or needs review. Missing information is never a pass.

tia/calibration.py

Reviewers can mark findings confirmed or false alarm; the calibration report shows how often each rule was right.

Step 9. Decide what to test

Turn findings into a test plan in testers' words

Goes inThe findings, the map and the test facts
→
Comes outA test scope, rule gaps, the written test cases to run again, and automation material

Findings speak about code. Testers think about screens, reports and test cases. So TIA writes a test scope: the screens and addresses a person can test, named the way the team named them ("Payments screen", "Monthly statement PDF"), with the existing tests for each.

It also checks business rules: when one service applies a rule to some data and another service using the same data does not, TIA raises the question. In our example the statement hides disputed payments and the portal shows them.

From the testers' own written test cases, it picks the ones to run again and says why, and lists the ones it could not match for a person to review. For automation testers it lists each screen's fields, how to find each one on the page, the inputs each address accepts, and can draft a browser test script for a user flow.

Step 10. Add evidence, list unknowns

Use test results and deployments; say what is not known

Goes inThe findings and the evidence records TIA holds
→
Comes outFindings with test states and deployment notes, and the list of unknowns

Code alone cannot say whether a test passed last night or which version runs in production. The build and release tools know, and they can send that information to TIA beforehand: test results, coverage, deployments, builds, live traffic between services, incidents. TIA uses what it holds and records exactly which records it used. It never fetches anything in the middle of an analysis.

Every report then ends with its unknowns: what TIA could not see that might change the answer. A short report is never mistaken for a safe one. If there are unknowns that limit confidence, the status says complete_with_gaps, not complete.

Step 11. Save the report

Store it with proof of what it was based on

Goes inThe report and everything it used
→
Comes outA stored report, its snapshot id and an audit-log entry

The finished report is saved together with a list of exactly what it was based on: the commit of every repository, the versions of TIA's readers, the map version, the evidence records and the settings. That list has an ID (the snapshot).

Later, TIA can re-run the analysis from that list and show the result is identical. That is the answer to "how do I trust this?".

Important events (an analysis requested, a setting changed) are written to a sealed log: each entry is sealed together with the one before it, so changing or deleting an old entry is detected.

tia/impact.py (end of _analyze)

Builds the snapshot id as a hash of every input: commits, reader versions, map version, stale links, evidence record ids and the configuration.

tia/store.py · put_snapshot, put_analysis, audit

Saves the snapshot and the report in PostgreSQL, bound to the organisation; appends to the audit log, where each entry's seal (HMAC-SHA256) includes the previous one.

tia/analysis_service.py · pin_analysis, reproduce

Keeps every analysed commit reachable in TIA's copies; re-runs an old analysis on its snapshot and compares.

Every row carries its organisation's id; the database itself refuses to show one organisation's rows to another.

Step 12. Publish and share

A pull-request comment, a web page, and answers for other tools

Goes inThe stored report
→
Comes outA pull-request comment and status, a shareable page, and answers for assistants and other systems

The result goes where people and tools are:

  • On the pull request: one comment, updated on every push, plus a status. It is advisory unless the organisation makes its release rules blocking.
  • On a web page that can be shared or printed.
  • To other tools: coding assistants (through MCP), Knowledge Fabric, scripts, and a copy of the map in Neo4j.

Everyone sees only what they may: a repository a reader cannot open is replaced by a count, never shown.
